# 决策 44. 动图页把普通视频也列进列表：「视频 N」+ 默认不勾 + 下载前确认（2026-10-19）

> 决策索引：[DEVELOPMENT.md](../DEVELOPMENT.md#决策索引)（编号与代码注释里的「决策 44」一一对应）

## 背景

用户提出：「能否把视频也当做动图，在动图列表里按『视频 1』『视频 2』（以此类推）命名，默认
不勾选视频格式，若用户勾选视频格式，点击『下载』后会弹窗提示用户，若用户仍选择转 GIF 则用
best quality 的视频流来转 GIF」。

现状（决策 30 建立的口径）：`_looks_like_animated` 把「无时长 + 无分辨率」判为动图，
`fetch_gif_items` 只列出动图、`download_and_convert_gif` 也只下载动图——同一条推文里的
普通视频既不显示、也不下载。这个口径来自 2026-10-07 的实测（推文「2 动图 + 1 个 4K 视频」
只产出 2 个 GIF），目的是防止用户没要的视频被顺手转成体积巨大的 GIF。

新需求把「视频」从「隐式跳过」改成「显式可见、显式勾选、显式确认」：用户能看到推文里
到底有几个视频，但下载与否完全由他自己决定，且视频默认不勾选。

## 用户拍板的五个细节

| # | 问题 | 结论 |
|---|---|---|
| 1 | 「视频 N」用在哪些地方 | **只做列表显示名**。输出 GIF 文件名仍取 yt-dlp 下载到的 mp4 标题 |
| 2 | 视频转码用哪档画质 | **沿用页面当前所选质量档**，不强制「最佳质量」 |
| 3 | 要不要加时长/体积保护限制 | **不加** |
| 4 | 「全选」要不要把视频也选上 | **不选**。视频只能手动逐个勾选 |
| 5 | 弹窗时机 | **点「下载」时弹**，勾选视频的那一刻不弹 |

另外用户追加一条版式要求（m00442）：「**动图列表要保证动图在视频前**」——动图排在连续
前段、视频排在后段，同类型内各自保持原始条目次序。

## 结论

### 1. 条目判定：新增 `_entry_kind`，两档分类（core/functions.py）

```python
def _entry_kind(entry):
    if _looks_like_animated(entry):
        return 'gif'
    if entry.get('duration') not in (None, 0):
        return 'video'
    return None
```

- `_looks_like_animated` **原样保留**，它仍是「是不是动图」的唯一回答者；`_entry_kind`
  只是在其上加一档。
- 判视频**只认「有明确时长」**。原因：X 的**图片**条目同样没有时长、没有分辨率，与动图
  在元数据上无法区分——它们会沿用旧口径落进 `'gif'` 档（下载时被格式串 `b[ext=mp4]/b`
  自然筛掉，不是本次引入的行为）。只有 `duration not in (None, 0)` 才敢认定是视频。
  误判方向仍刻意保守——解析不出时长的视频会被当成动图（多下一个动图，不会漏），但
  绝不会把图片伪造成「视频 N」。
- 有分辨率但无时长 → `None`（罕见条目），既不列动图也不列视频。

`fetch_gif_items` 的返回项新增 `kind`（`'gif' | 'video'`）、`visible` 视频的 `video_no`
（按视频出现顺序从 1 编号，与动图的原始条目序号各自独立计数）。**排序在函数内完成**：
`items = gifs + videos`——页面把列表顺序直接当网格顺序，排序放在数据层比放在页面层更
不容易被后续改动破坏；`index` 仍是**原始条目序号**，不受排序影响（下载时以
`--playlist-items` 回传，必须与 yt-dlp 看到的条目次序一致）。

日志同步改为「条目解析完成: {title}, 共 {n} 个动图、{m} 个视频」。

### 2. 下载：放行视频条目（core/functions.py）

`download_and_convert_gif` 的 ① 识别段：

```python
kinds = {i + 1: _entry_kind(e) for i, e in enumerate(entries)}
convertible = [i for i, k in kinds.items() if k is not None]
```

`animated` 更名为 `convertible`（动图 + 视频），`selected_indexes` 与它求交集后成为
`downloadable`，再拼 `--playlist-items`。**函数本身不再拦截视频**——「视频要不要转」
的判断全部上移到页面（默认不勾 + 勾了弹窗），因为任务函数拿不到 UI 状态，在这里再做
一次拦截只会造成「页面放行、内核又拒」的双份口径。若 `selected_indexes` 为空（老调用 /
其他入口）则 `downloadable = convertible`，即全部下载。

日志补了计数与提示：
- `[GIF] 共 {N} 个条目，将下载 {M} 个（动图 a 个、视频 b 个）`
- 有视频时额外一行 `[GIF] 注意：其中 b 个为普通视频，转 GIF 可能体积较大、耗时较长`

错误文案同步改成「该链接没有动图或视频（推文只含图片），已跳过」、
「选中的条目无法转换（可能链接已更换），请重新解析」。

### 3. 页面：卡片默认勾选按 kind 决定（pages/gif_page.py）

- `GifItemCard.__init__` 里 `self._checked = self.kind != 'video'`——**默认勾选口径从
  「页面统一 `set_checked(True)`」搬到卡片自身**。原先 `_build_cards` 里那句
  `card.set_checked(True)` 已删除，否则会把视频也选上。
- 显示名：动图沿用 `动图 {index}`；视频用 `视频 {video_no}`（`fetch_gif_items` 给的
  视频内序号），两者各自从 1 开始。
- 卡片**不显示视频时长**。理由与决策 30 一致：动图永远没有时长，加了标签也只有视频
  会有；而视频时长属于常规信息，不是本功能的决策点，加进来反而让卡片高度不一致
  （`AdaptiveFlowLayout` 只用 `sizeHint().height()` 定高）。

### 4. 「全选/全不选」的作用域 = 动图（pages/gif_page.py）

- `_gif_indexes()` 给出「有动图时只有动图，纯视频链接才退回全部条目」的作用域。
- 「全选」**跳过视频**（第 4 点拍板）：全选是批量便利操作，不能顺便把用户明确排除的
  视频带上。
- 「全不选」**清空全部**（含用户手动勾的视频），否则按钮会变成「点不干净」。
- 按钮文案与 `selection_hint` 都按作用域算：提示文案改为
  `共 {n_gif} 个动图、{n_video} 个视频 · 已选 {n} 个`（缺一档时只显示存在的那档）。
- 纯视频链接没有动图可选，作用域退回全部条目，让「全选」仍然可用。

### 5. 下载前确认弹窗（pages/gif_page.py `_start_download`）

位置在「校验通过、拿到 `selected_indexes`」之后、「读质量档/建任务」之前——取消必须
**整单不入队**，而不是入队后立刻取消。

```python
n_gif, n_video = self._count_kinds(selected_indexes)
if n_video:
    box = qfw.MessageBox("视频将转为 GIF", "…预折行正文…", self.window())
    box.yesButton.setText("仍要转 GIF")
    box.cancelButton.setText("返回修改")
    if not box.exec():
        return
```

- 复用决策 38（`youtube_page` mkv 风险弹窗）的写法：`qfw.MessageBox` + 自定按钮文案。
- 正文**手动预折行**：`qfw.MessageBox` 的宽度取「未折行文本」的 `sizeHint`，不折行会
  撑到 ~700px（决策 38 已踩过）。
- 文案带上下文：`共选中 N 个条目，其中 M 个为普通视频` / `选中的 M 个均为普通视频`，
  再加体积与耗时提醒。
- 取消 → `return`，用户回页面自己取消勾选再点下载（不做「自动帮他取消勾选后继续」，
  那样等于替用户做决定）。

### 6. 沿用的质量档与输出名

- 质量：`download_and_convert_gif` 的 `quality` 参数不变，页面传当前档位。用户原话
  「用 best quality 的视频流来转 GIF」只影响**下载哪条流**——`download_youtube` 的
  格式串一直是 `"b[ext=mp4]/b"`，即 yt-dlp 判定的 best，本来就是最高画质流；
  转码档位仍由页面决定（第 2 点拍板）。
- 输出名：`_gif_path(mp4)` 取 mp4 的 stem，与「视频 N」显示名无关（第 1 点拍板）。
  因此同一条推文的动图与视频转出的 GIF 文件名仍各自取自原媒体标题。

## 文案同步（同批改动）

标题/说明/占位符从「X 动图下载 / 粘贴 X 动图链接」改为「X 链接 / 粘贴 X 推文链接」，
因为现在一个链接里可能只有视频没有动图：

| 位置 | 新文案 |
|---|---|
| 副标题 | 粘贴 X 链接，解析后勾选要下载的动图（视频默认不选），自动转为 GIF |
| URL 占位符 | 粘贴 X/Twitter 推文链接，如 https://x.com/xxx/status/123 |
| 空态 | 还没有解析条目 / 请粘贴 X 链接并解析 |
| 解析日志 | 正在解析条目列表（读取标题/封面，不下载媒体）... |
| 解析结果日志 | 解析到 a 个动图、b 个视频；动图默认勾选，视频需手动勾选 |
| 空结果 | 该链接没有动图或视频（推文只含图片） |
| 入队 InfoBar | 共 N 个条目，下载完成后自动转码为 GIF |

## 风险与已知边界

- **判定依赖实测**：`_entry_kind` 立足「X 动图无时长、普通视频有时长」这一实测事实。
  若 X 改版让 animated_gif 带上时长，真动图会被判成视频（降级为「默认不选」，不会
  误下载）；若普通视频解析不出时长，会被判成动图（默认勾上，会被顺手转 GIF）——
  后者是旧口径就有的风险，本次未新增。
- **体积/时长无保护**（第 3 点拍板）：4K 长视频转 GIF 可能极慢、体积极大。缓解手段
  只有下载前弹窗里那句提醒，没有硬性上限。
- **图片条目与动图无法区分**：图片沿用旧口径落进 `'gif'` 档，会以「动图 N」出现在
  列表里（旧版也是同样的行为）。区别是下载阶段由 yt-dlp 的 `b[ext=mp4]/b` 筛掉，
  不会真的产出图片转出的 GIF。
